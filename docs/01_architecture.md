# معمارية OmniTune Engine (مسبك الذكاء)

## الهدف
بناء محرك تخصيص وضبط نماذج اللغة الكبيرة بشكل معياري وقابل للتوسع، مع دعم التشغيل غير المتزامن حتى لا تتعطل واجهات API أثناء مهام التدريب الطويلة.

## الفصل الطبقي (Clean Architecture)

- **`/core`**: يحتوي العقود (Interfaces) والنماذج المشتركة فقط.
  - السبب: فصل المنطق الجوهري عن التفاصيل التنفيذية يمنع الترابط الصلب ويُسهل الاختبار والاستبدال.
- **`/data_pipeline`**: محولات إدخال البيانات (Adapters) من أي مصدر.
  - السبب: تطبيق نمط Adapter يجعل مسار التدريب غير مرتبط بمصدر بيانات محدد (SQL/JSON/PDF/Vector DB).
- **`/trainer`**: تنفيذ محرك التدريب الفعلي.
  - السبب: عزل تقنيات التدريب (مثل Unsloth) عن واجهة API يقلل أثر التغييرات المستقبلية.
- **`/api`**: طبقة orchestration واستقبال الطلبات وتشغيل المهام الخلفية.
  - السبب: الحفاظ على استجابة سريعة للعميل مع تفويض المهام الطويلة إلى المعالجة الخلفية.

## لماذا Unsloth؟
- لأنه مُحسّن لذاكرة GPU ويقدم أداء عالياً في إعدادات LoRA/QLoRA.
- مناسب عملياً لقيود 24GB VRAM مع نماذج مثل Qwen-2.5-7B/14B.
- يقلل كلفة الذاكرة والزمن مقارنةً بمسارات تدريب تقليدية في نفس الفئة.

## لماذا المعالجة الخلفية؟
- التدريب عملية طويلة وقد تمتد لدقائق/ساعات.
- التنفيذ المتزامن داخل طلب HTTP يسبب timeout ويضعف تجربة المستخدم.
- استخدام FastAPI BackgroundTasks كمرحلة تأسيس يحقق البساطة، ويمكن لاحقاً استبداله بـ Celery/Redis بسهولة دون كسر العقود الأساسية.
